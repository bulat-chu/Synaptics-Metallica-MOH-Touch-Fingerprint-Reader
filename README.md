# 06cb:00a2 Synaptics, Inc. Metallica MOH Touch Fingerprint Reader


Из Linux удалось провести TLS-сессию с сенсором `06cb:00a2` и получить от него зашифрованные ответы. Для этого использовалось существующее сопряжение с вашим T590, во флэш сенсора мы ничего не писали. Распознавания пальца пока нет. Ниже отмечено, что проверено нами, а что только предположение.

## Что привело к результату

1. **Диагностика.** python-validity отвечал `No matching devices found`, штатный `fprintd` показывал `No devices available`: ни тот, ни другой драйвер этот ID не знает. Сторонние треды (Validity90 #34, форум Zorin) подтвердили, что это MOH-сенсор без готового драйвера.
2. **Windows-драйвер на T590.** Нужный пакет Lenovo ставится по `USB\VID_06CB&PID_00A2&REV_0164`. На первой машине был Code 31 (причину так и не нашли, версия про SGX не подтвердилась), на T590 драйвер заработал.
3. **Захват USB.** Wireshark с USBPcap (обычная, не портативная установка) записал полный сеанс: инициализацию, добавление пальца, проверку.
4. **Разбор протокола.** Захват ничего не расшифровывали, но по порядку команд и по формату TLS он сошёлся с python-validity шаг в шаг.
5. **Дамп флэша из захвата.** Ответ на чтение раздела 1 разобрался на блоки, у каждого сошёлся SHA-256, а ключ сенсора проверился публичным ключом прошивки из python-validity.
6. **Ключ хоста.** Имя продукта и серийник T590 (с учётом регистра) подошли к HMAC блока 4, ключ расшифровался.
7. **Скрипт `probe_00a2.py`.** Три этапа на Linux: ответы совпали с захватом, handshake прошёл, ответ на `75` дал тип сенсора `0x199`.

## Как устроено взаимодействие

**USB.** Один интерфейс класса vendor-specific, пять эндпоинтов:
- `0x01` bulk OUT: команды хоста.
- `0x81` bulk IN: ответы и данные. Первые 2 байта ответа это статус (`0000` значит успех).
- `0x83` interrupt IN: 5-байтные события во время сканирования (повторяющиеся серии вроде `02 00 40 10 00`, `03 40 01 00 00`). Их смысл мы не расшифровывали.
- `0x82` и `0x84` в захвате не использовались, зачем они, не знаю.

**Открытая фаза (до TLS).** Хост по очереди спрашивает: `01` (ROM info: версия 6.7, build 164, product `0x30`), `19`, `43 02` (информация о прошивке, раздел 2: версия 1.3, 7 модулей), затем шлёт 581-байтный блоб инициализации, `3e` (76 байт, назначение неизвестно) и читает `40 01…` (раздел 1, адрес 0, 0x1000 байт).

**Что лежит в разделе 1 флэша** (блоки 0, 4, 3, 5, 1, 2, 6, у каждого свой SHA-256):
- Блок 4: приватный ключ хоста, зашифрован AES-CBC и защищён HMAC. Ключи для этого выводятся из зашитой константы и из имени продукта с серийником компьютера. Поэтому сенсор «привязан» к конкретной машине.
- Блок 3: клиентский сертификат (хост отправляет именно его в handshake).
- Блок 6: публичный ECDH-ключ сенсора, подписанный ключом прошивки.
- Блоки 1 и 2 пустые, назначение блока 5 мы не разбирали.

**TLS 1.2 поверх USB.** Каждое сообщение уходит с префиксом `44 00 00 00`. Набор `TLS_ECDH_ECDSA_WITH_AES_256_CBC_SHA`, кривая P-256. Хост шлёт сертификат, ключевой обмен, подпись и Finished. Сенсор доверяет только хосту, которого сопрягли, а хост проверяет подпись ключа сенсора. После handshake идут записи `17 03 03`: команды и данные зашифрованы.

**Данные.** После handshake по `0x81` идут записи по ~23 КБ (в сеансе добавления пальца их десятки). Похоже на кадры изображения, но формат мы не видели.

## Что остаётся неизвестным
- Формат кадров и команды захвата изображения.
- Назначение `19`, `3e`, блока 5 и событий на `0x83`.
- ??? Как именно Windows-драйвер сопоставляет отпечатки. «MOH» (Match On Host) означает сопоставление на хосте, это следует из названия и слов Lenovo, но подтверждения в самом протоколе мы не получили. Получается MIS - Match In Sensor (?)
- Почему на первой машине был Code 31.

Всё это получено из ваших захватов и кода python-validity, официальной документации у Synaptics нет. Не публикуйте `tls_flash.bin`, серийник и имя компьютера: по ним выводится ключ хоста.

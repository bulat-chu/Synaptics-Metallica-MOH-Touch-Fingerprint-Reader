## 0. Коротко (TL;DR)
- Сенсор 06cb:00a2 в Linux **работает на уровне протокола**: мы свой клиентом (код python-validity + мои скрипты) проводим TLS-сессию по
  существующему сопряжению, калибруем сенсор в памяти и снимаем полные кадры 112×112 (8 бит). Во флэш сенсора мы ничего не писали.
- Драйвера libfprint для него нет. Распознавание проверено **офлайн на NBIS** (то, что использует libfprint): ложных принятий нет,
  но свои пальцы подтверждаются не очень уверенно (см. п. 7). Нужны улучшения (предобработка, несколько касаний при записи, порог).
- Открытая загадка: после кадра драйвер Windows читает ещё два блока по ~23 КБ (похоже на 152×152 = 23104; возможно, обработанные кадры).
  Команды, которыми это запрашивается, неизвестны.
- До «подключил и fprintd работает» осталось: разобраться с 23 КБ, выбрать способ сопряжения с Linux-хостом (запись во флэш), хранение калибровки,
  алгоритм/порог сопоставления, драйвер (libfprint на C или бэкенд open-fprintd на Python).

## 1. Цель
Сенсор работает в Linux **без «танцев с бубном»**: `fprintd-enroll`/`fprintd-verify`. Идеал: драйвер в libfprint (C). Промежуточный вариант: Python-прототип/бэкенд.

## 2. Железо и окружение
- Сенсор: `06cb:00a2`, `bcdDevice 1.64`; lsusb: «Synaptics, Inc. Metallica MOH Touch Fingerprint Reader». USB full-speed, интерфейс vendor-specific (class ff, sub 00, prot 00).
  Эндпоинты: `0x01` bulk OUT (команды), `0x81` bulk IN (ответы), `0x82` bulk IN (python-validity читает по нему калибровочные кадры; в захвате Windows данных не нёс),
  `0x83` interrupt IN (5-байтные события), `0x84` interrupt IN (не использовался).
- Linux: Arch, хост `saturn-workstation`, Python 3.14, папка проекта `~/MyFiles/Creating/ThinkPad-Revive/Fprint/L380/`.
  Штатные `fprintd 1.94.5` + `libfprint 1.94.100` восстановлены (`fprintd-list` → `No devices available`, это ожидаемо). python-validity/open-fprintd из AUR удалены;
  используется только клон `git clone https://github.com/uunicorn/python-validity` в папке проекта (не установка в систему).
  Нужны пакеты: `python-pyusb python-cryptography python-pillow`; для теста сопоставления NBIS (`mindtct`, `bozorth3`, у меня в /usr/bin).
- Windows-проверка: ThinkPad T590. Драйвер Lenovo для сенсора заработал после **отключения Intel SGX в BIOS**. На первой Windows-машине тот же пакет давал Code 31
  (причина не выяснена; гипотеза «нужен SGX» не подтвердилась). Пакет: `synawudfbiousblenovosgxprod.inf` 5.2.326.26 (12.12.2022), ещё пробовался 5.2.324.26;
  совпадает с `USB\VID_06CB&PID_00A2&REV_0164`; в составе `synaWudfBioUsb`, `SynaSmi.sys`, `6_07f_lenovo_sm_qm.xpfwext`.
- Захват USB: Wireshark + USBPcap (обычная установка, не портативная; портативная версия снимала пустой pcap).

## 3. Хронология (кратко)
1. python-validity 0.15: «No matching devices found»; штатный libfprint: «No devices available». Откатил на штатный fprintd.
2. Треды Validity90 #34, форум Zorin: драйвера для 00a2 нет; Lenovo писала, что драйвера для Linux нет.

4. Разбор захвата: порядок команд совпал с python-validity; TLS 1.2 поверх USB; в захвате нашлась структура флэша; ключ хоста расшифровался с данными T590.
5. Свой клиент под Linux: этапы 1–6 `probe_00a2.py`: TLS, калибровка в памяти, захват, кадр.
6. Серии кадров `capture_series.py`; оценка на NBIS `nbis_eval.py` (три набора по 25 кадров).

## 4. Протокол (с уровнем уверенности: [подтв.] проверено на живом сенсоре или данных; [гипотеза])
### 4.1 Открытая часть (до TLS) [подтв.]
Порядок в начале сессии (так шлёт драйвер Windows, так же делает `send_init()` в python-validity):
| Команда OUT | Ответ |
|---|---|
| `01` | 38 байт: статус `0000`, timestamp 1415491824, build 164, major 6, minor 7, product 0x30 |
| `19` | 68 байт; последние 4 байта меняются (счётчик/часы?); после сброса сенсора начало `00000003 01020001`, как в захвате Windows |
| `43 02` | 96 байт: инфо раздела 2 (прошивка-расширение): версия 1.3, 7 модулей |
| блок 581 байт, начало `06 02 00 00 01…` | `0000`. Берётся дословно из USB-захвата Windows (лежит в скриптах). Той же длины, что `init_hardcoded` для 097/09a/09d в python-validity, но совпадает с ним лишь частично (325 из 581 байт) |
| `3e` | 76 байт (назначение неизвестно; python-validity не использует) |
| `40 01 01 00 00 00 00 00 00 00 10 00 00` | чтение раздела флэша 1 (TLS-данные): 4104 байта (8 заголовок + 0x1000) |
Формат ответов: первые 2 байта статус (`0000` = успех); для `40`: `status(2) size(4, LE) 2 байта` + данные.

### 4.2 Флэш-раздел 1 и сопряжение [подтв.]
- 4096 байт делятся на блоки по схеме python-validity (`make_tls_flash`): id 0, 4, 3, 5, 1, 2, 6, у каждого блока SHA-256 сходится.
  Блок 4 (161 байт, префикс `02`) приватный ключ хоста (зашифрован, HMAC); блок 3 (184) клиентский сертификат (его же драйвер Windows шлёт в handshake);
  блок 6 (400) публичный ECDH-ключ сенсора с подписью; блок 5 (420), блоки 1 и 2 (по 256 нулей).
- Подпись блока 6 проверяется публичным ключом прошивки из `tls.py` python-validity ⇒ та же цепочка доверия, что у поддерживаемых моделей.
- Ключ хоста выводится из зашитых констант python-validity (`password_hardcoded`, `gwk_sign_hardcoded` в `tls.py`) и из
  `hw_key = имя_продукта + \0 + серийник + \0`. HMAC блока 4 сошёлся для данных моего T590 (регистр важен). Сенсор сопряжён с T590.
  Проверка офлайн: `check_hwkey.py` + `tls_flash.bin` → `MATCH`. С данными T590 приватный ключ расшифровывается, его публичная точка лежит в сертификате (блок 3).

### 4.3 TLS [подтв.]
TLS 1.2 поверх USB: `TLS_ECDH_ECDSA_WITH_AES_256_CBC_SHA` (0xc005), кривая P-256, сообщения handshake идут с префиксом `44 00 00 00`.
Из Linux handshake проходит по существующему сопряжению; после него `01`, `75`, `43 02` по TLS работают. Расшифровать **уже снятые** записи Windows нельзя: сессионные ключи эфемерные (нужен дамп памяти драйвера во время сеанса).
Размеры на проводе (проверено): запись TLS = 5 байт заголовка + IV 16 + CBC(plaintext + MAC 32 + padding до 16). Так размеры записей из захвата
превращаются в длину открытого текста (используется для сверки команд).

### 4.4 Идентификация [подтв.]
`75` по TLS → `0000 00000000 6a00 9001` (major 0x190, minor 0x6a) → в `hw_tables.dev_info_lookup` это тип `0x199`, «57K0 FM-3380-001».
Факторные данные (`6f`, тег 0x0e00): подтеги 2, 3, 5, 8, 12, 15. Подтег 2 = ответ `75`; подтег 8 = `0x0199`; подтег 3 = 4+112 байт (112 = line_width типа 0x199); подтега 7 нет (необязателен).
ROM info 6.7 build 164: то же значение сообщает 009a на ThinkPad P52 (issue fprintd/libfprint #113).

### 4.5 Калибровка и захват [подтв.]
- Раздел флэша 6 хранит «clean slate» в формате python-validity (магия 0x5002, длина 13444 = 13440 + 4; 13440 = 112 строк × 120 байт для типа 0x199). Windows уже калибровал сенсор.
- `calib_data` (13440 байт) из раздела 6 восстановить нельзя (в разделе 6 другое: усреднённый пустой кадр), поэтому калибруем **только в памяти**:
  в `sensor.open()` запись во флэш делают `persist_clean_slate` и `save`, они отключены подменой. Калибровка: 4 снимка без пальца (кадры читаются по `0x82`).
- Команда захвата `sensor.build_cmd_02(CaptureMode.IDENTIFY)` для типа 0x199 даёт 13741 байт (ответ сенсора 1966 байт). Размеры записей Windows согласуются: 13797 на проводе ↔ 13729 открытого текста у python-validity (в пределах дополнения), ответ 2021 ↔ 1966.
- События `0x83`: `00 00 00 00 00` (старт) → `02 00 40 10 00` (палец) → `03 40 01 00 00` → `03 42 04 00 40` (**готово**, бит 4 в 3-м байте). Совпадает с логикой `capture()` python-validity.
- Кадр: команда `51 00 20 00 00` (в python-validity `get_prg_status2`) возвращает 8198 байт = статус 2 + длина 4 (8192) + 12-байтный заголовок `x=112, y=112, w1=333, w2=8, error=0` + 8180 пикселей.
  Следующее `51 <длина uint32 LE>` (`51 0c 31 00 00` = 12556) возвращает остаток 4364 байта. Итого 8180 + 4364 = 12544 = 112×112 пикселей, 8 бит, строки по 112. Читаются **последовательно** (буфер результата).
  Размеры 8256 и 4437 на проводе в захвате Windows совпали с этими чтениями: драйвер Windows делает то же.
- Штатный `capture()` python-validity падает на `unpack('<HHHHL', res)`: у 00a2 к 12 байтам статуса приложены пиксели.

### 4.6 Цикл одного касания в захвате Windows [подтв. по размерам записей, не по содержимому]
(1) `02` 13797 → ответ 2021; события 0x83; (2) два чтения кадра (8256 + 4437); (3) короткие обмены; (4) дважды подряд: команда ~90 байт открытого текста → ответ ~100 байт, затем короткая команда (5–15 байт) → **ответ 23173 байта**;
(5) ещё короткие обмены, команда ~110–125 байт, следующее касание. На этапе проверки хост отправляет сенсору крупный блок 23205 байт и ещё пять по 2757.
Размер 23173 = открытый текст ~23110 = 6 + **23104 = 152×152**. 152/112 = 1,357 = 500 dpi / 368 dpi. [гипотеза] сенсор/драйвер отдаёт увеличенный (и, возможно, обработанный) кадр 152×152; совпадение размера случайным может быть с вероятностью в несколько процентов.

## 5. Изображения и разрешение
- Кадры чёткие: в контактной зоне линии хорошо видны. Артефакты: шумные полосы у верхнего (и у нижнего) края части кадров, слабые линии. Склейка двух чтений проверена: шва нет.
- dpi в источниках не найден (для 009a тоже). Оценка по периоду гребней 7–8 пикселей (0,45–0,55 мм): ~340–410 dpi (±25%); по гипотезе 152/112: ~368 dpi.
- Корреляция изображений (сдвиги, повороты ±40°; 15 кадров, 2 пальца): один палец, медиана 0,88; разные пальцы, медиана 0,52, максимум 0,61; для каждого кадра лучший кадр того же пальца лучше лучшего чужого (15 из 15).

## 6. Сопоставление на NBIS: метод
`nbis_eval.py`: кадры не режутся (по умолчанию `--crop-top 0`), увеличиваются в `--scale` раз (≈500 dpi-эквивалент), `mindtct` → `.xyt`, `bozorth3` по всем парам (в обе стороны, максимум).
Метрики: «same finger / different finger» по парам; AUC; **идентификация** (кадр против остальных касаний каждого пальца; все нули или ничья = «undecided»); **проверка**: касание принимается, если лучшая оценка против остальных касаний этого пальца ≥ порога.
Ключи: `--scales 1.7,2.0`, `--invert-too` (инверсия яркости результата не меняла), `--threshold` (подсчёт «принято»; в libfprint, по памяти, порог по умолчанию 40, не проверено; у драйверов, насколько помню, его можно менять).

## 8. Открытые вопросы / гипотезы
1. **Два блока по 23104 байта после кадра** (152×152?): какие команды их запрашивают (команда ~90 байт → ответ ~100 байт, затем короткая команда чтения).
   Эксперимент: `capture_series.py --extra-read 23104` (после кадра пробует `51 <N>`; скорее всего, ответит ошибкой/пусто, т.к. подготовительных команд мы не знаем).
   Надёжный способ: расшифровать сеанс Windows (дамп памяти `WUDFHost.exe` с загруженным `synaWudfBioUsb` через Process Explorer «Create Full Dump» сразу после handshake + одновременный USBPcap-захват;
   затем поиск master secret / ключей по дампу с проверкой по сообщению Finished). Скрипта поиска ключей ещё нет (писать после получения дампа).
2. Смысл `19`, `3e`, блока 5 флэша, `0x82`/`0x84`; блок 23205 и 2757 при проверке.
3. Где идёт сопоставление: сенсор отдаёт картинку хосту (подтв.), но хост отправляет сенсору крупные блоки при проверке. Формулировка «MOH = сопоставление на хосте» **не подтверждена**.
4. Как сопрягать сенсор с Linux-хостом (нужна запись во флэш; Windows на T590 придётся сопрягать заново, делает ли драйвер Windows это сам, неизвестно).
5. Хранение калибровки (сейчас пересчёт на каждый запуск: 4 снимка).
6. Как libfprint справляется с малой площадью кадра: в старом баге по 138a:0091 писали, что libfprint урезал 112×112 до 96×96 и этого не хватало (bugs.freedesktop.org 99462). Для 138a:0090 в README Validity90 упомянут драйвер libfprint с сопоставлением на хосте.

## 10. Правила безопасности
- Не запускать `factory-reset.py`, `validity-sensors-firmware`, `init_flash` и любые записи во флэш/прошивку сенсора, пока я явно не согласился.
